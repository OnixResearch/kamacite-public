# Documentation Pipeline Specification

## Purpose

Extend Kamacite documentation IR with autogenerated documentation inputs for Rust, Nickel, and Steel source envelopes.

## Requirements

### Requirement: Language documentation facts are canonical collector outputs

r[kamacite.docs.language_facts.schema] Kamacite MUST define a Preserves-backed `language-documentation-facts` artifact for bounded documentation facts collected from Rust, Nickel, and Steel source envelopes. The artifact MUST bind schema identity, source-envelope identities, source spans, collector identity, language label, stable item identifiers, symbol paths, title text, signature or contract summaries, prose blocks, code blocks, runnable-cell references, links, dependency identities, diagnostics, checked laws, and non-claims.

#### Scenario: Collected facts remain separate from source identity

r[kamacite.docs.language_facts.source_binding]

- GIVEN a collector extracts documentation facts from a Rust, Nickel, or Steel source envelope
- WHEN Kamacite computes the collected facts identity
- THEN the facts identity MUST remain separate from the source-envelope identity and MUST bind the source-envelope BLAKE3 identity as an input rather than replacing it.

#### Scenario: Unsupported language fails closed

r[kamacite.docs.language_facts.unsupported_language]

- GIVEN a documentation facts artifact declares a language outside the admitted Rust, Nickel, and Steel collector set
- WHEN Kamacite validates the artifact
- THEN validation MUST fail closed with a deterministic unsupported-language diagnostic before assembling documentation IR.

#### Scenario: Collector identity drift fails closed

r[kamacite.docs.language_facts.collector_drift]

- GIVEN a language documentation facts artifact was generated by one collector identity
- WHEN a later check observes a different collector identity, collector profile, or source-envelope dependency for the same declared facts identity
- THEN Kamacite MUST report deterministic collector-drift diagnostics and MUST NOT trust the stale generated facts.

### Requirement: Language documentation facts validation is pure

r[kamacite.docs.language_facts.validation] Kamacite MUST validate language documentation facts with pure deterministic core functions over in-memory inputs. Validation MUST check collector identity, source-envelope links, source spans, item identifiers, signatures or contract summaries, links, runnable-cell references, dependency identities, diagnostics, checked laws, and non-claims without filesystem, process, network, clock, random, credential, evaluator, compiler, stdout, stderr, or mutation access.

#### Scenario: Non-claims are preserved on collected facts

r[kamacite.docs.language_facts.non_claims]

- GIVEN a Rust, Nickel, or Steel collector emits documentation facts
- WHEN Kamacite validates the facts artifact or exports a related receipt
- THEN the artifact MUST preserve non-claims that collected documentation facts do not prove compiler correctness, evaluator soundness, runtime behavior, authorization, source-language semantic equivalence, or rendered-output authority.

### Requirement: Collection receipts bind source and collector evidence

r[kamacite.docs.collection_receipts] Kamacite MUST emit deterministic collection receipts for trusted language documentation facts. A collection receipt MUST bind source-envelope identities, collector identity, collector profile, dependency identities, facts identity, diagnostics, checked laws, receipt identity, and non-claims.

#### Scenario: Collection receipt rejects missing facts identity

r[kamacite.docs.collection_receipts.missing_facts]

- GIVEN a collection receipt omits the generated language documentation facts identity
- WHEN Kamacite validates the receipt
- THEN validation MUST fail closed before the facts can be assembled into documentation IR.

### Requirement: Nickel-authored docs configuration controls generation

r[kamacite.docs.config.nickel] Kamacite MUST use Nickel-authored typed configuration contracts for autogenerated documentation source roots, language labels, collector profiles, output formats, page grouping, link policy, run profile, output directories, and update policy. Runtime JSON or other projections MAY be produced for tool compatibility, but Nickel configuration MUST remain the reviewable source of truth.

#### Scenario: CLI consumes checked docs configuration

r[kamacite.docs.command.config]

- GIVEN an operator invokes a documentation command with a docs configuration path
- WHEN the CLI loads the configuration
- THEN it MUST validate the Nickel-derived configuration against Kamacite contracts before collecting, checking, rendering, running cells, or updating generated artifacts.

#### Scenario: WASM runner profiles are declared in config

r[kamacite.docs.wasm_runner.config]

- GIVEN a documentation configuration admits WASM-backed runnable examples
- WHEN the CLI validates the configuration
- THEN the configuration MUST declare the admitted runner profile, engine identity policy, import policy, capability policy, and resource-limit policy before any WASM cell can run.

### Requirement: Documentation IR assembly from language facts is deterministic

r[kamacite.docs.ir_assembly] Kamacite MUST provide pure deterministic planning that assembles Rust, Nickel, and Steel language documentation facts into existing documentation IR pages, sections, anchors, links, runnable cells, dependencies, diagnostics, checked laws, and non-claims.

#### Scenario: Anchor assignment is stable across languages

r[kamacite.docs.ir_assembly.anchors]

- GIVEN equivalent language documentation facts are provided in any filesystem iteration order
- WHEN Kamacite assembles documentation IR
- THEN generated page, section, item, and runnable-cell anchors MUST be stable and duplicate anchors MUST fail closed with deterministic diagnostics.

#### Scenario: Cross-language links resolve by identity

r[kamacite.docs.ir_assembly.links]

- GIVEN a Rust item links to a Nickel contract, a Nickel example links to a Steel adapter, or a Steel host-function descriptor links to Rust validator evidence
- WHEN Kamacite assembles documentation IR
- THEN each link MUST resolve to an explicit item, source-envelope, facts, runnable-cell, or receipt identity and unknown or ambiguous links MUST fail closed.

#### Scenario: WASM targets bind into documentation IR

r[kamacite.docs.wasm_runner.ir_binding]

- GIVEN a language documentation facts artifact declares a runnable example with a WASM execution target
- WHEN Kamacite assembles documentation IR
- THEN the resulting runnable-cell descriptor MUST bind the source identity, WASM target identity, runner profile identity, expected result identity or diagnostic, dependencies, checked laws, and non-claims.

### Requirement: WASM runnable documentation execution is explicit and bounded

r[kamacite.docs.wasm_runner.schema] Kamacite MUST define Preserves-backed artifacts for WASM runner profiles and WASM runnable-cell execution records. The artifacts MUST bind module or component identity, engine identity, runner profile, declared imports, declared capabilities, resource limits, expected outputs or diagnostics, observed outputs or diagnostics, observed effects, dependency identities, checked laws, and non-claims.

r[kamacite.docs.wasm_runner.validation] Kamacite MUST validate WASM runner profiles and execution records with pure deterministic core functions over in-memory inputs. Validation MUST NOT invoke a WASM engine, read files, inspect the environment, access clocks, access random state, print output, or mutate generated artifacts.

r[kamacite.docs.wasm_runner.receipts] Kamacite MUST emit deterministic WASM cell execution receipts before trusting WASM-backed runnable documentation results. Receipts MUST bind the source-envelope identity, module or component identity, compiler or adapter identity when present, engine identity, runner profile, declared imports, declared capabilities, resource limits, observed outputs, diagnostics, checked laws, receipt identity, and non-claims.

#### Scenario: WASM is not canonical Kamacite IR

r[kamacite.docs.wasm_runner.non_claims]

- GIVEN a runnable documentation example executes through WASM
- WHEN Kamacite emits the cell receipt or renders the result in documentation
- THEN the receipt and rendered projection MUST state that WASM is an execution adapter target and MUST NOT substitute WASM module identity for source-envelope, language-facts, documentation IR, or receipt identity.

#### Scenario: Undeclared WASM imports fail closed

r[kamacite.docs.wasm_runner.effects]

- GIVEN a WASM-backed runnable cell imports host functions, WASI capabilities, filesystem access, network access, clock access, random access, credentials, compiler services, evaluator services, or mutation authority not declared by its runner profile
- WHEN Kamacite validates the execution record
- THEN validation MUST fail closed with deterministic undeclared-import or undeclared-capability diagnostics before trusting the cell receipt.

#### Scenario: WASM resource-limit violations fail closed

r[kamacite.docs.wasm_runner.resource_limits]

- GIVEN a WASM-backed runnable cell exceeds the configured fuel, memory, output-size, time, or effect budget for its run profile
- WHEN Kamacite validates the execution record
- THEN validation MUST fail closed with deterministic resource-limit diagnostics and MUST NOT update golden cell receipts unless explicit update mode is selected.

### Requirement: Rust documentation collector stays bounded

r[kamacite.docs.collectors.rust] Kamacite MAY collect Rust documentation facts from Rust source envelopes, rustdoc-compatible outputs, or bounded parser outputs, but the collector MUST classify those facts as documentation evidence and MUST NOT claim Rust compiler correctness, arbitrary program behavior, or cross-language semantic equivalence.

#### Scenario: Rust fixtures cover generated docs facts

r[kamacite.docs.collectors.rust.fixtures]

- GIVEN Rust source fixtures contain modules, functions, types, doc comments, signatures, examples, and source spans
- WHEN the Rust collector fixture runs or stored evidence is validated
- THEN Kamacite MUST accept matching positive facts and reject stale hashes, duplicate item identifiers, missing source spans, and overclaims.

### Requirement: Nickel documentation collector stays bounded

r[kamacite.docs.collectors.nickel] Kamacite MAY collect Nickel documentation facts from Nickel source envelopes, comments, contracts, fields, metadata, examples, and reference CLI projections, but the collector MUST NOT reimplement Nickel evaluation semantics or claim arbitrary Nickel semantic equivalence.

#### Scenario: Nickel fixtures cover generated docs facts

r[kamacite.docs.collectors.nickel.fixtures]

- GIVEN Nickel source fixtures contain contracts, fields, metadata, comments, examples, and source spans
- WHEN the Nickel collector fixture runs or stored evidence is validated
- THEN Kamacite MUST accept matching positive facts and reject stale hashes, unsupported projections, missing evaluator identities, and overclaims.

### Requirement: Steel documentation collector stays bounded

r[kamacite.docs.collectors.steel] Kamacite MAY collect Steel documentation facts from Steel source envelopes, module exports, definitions, contracts, adapter descriptors, host-function descriptors, examples, and source spans, but the collector MUST NOT treat Steel bytecode, opaque closures, ambient host functions, or JSON strings as canonical Kamacite IR.

#### Scenario: Steel fixtures cover generated docs facts

r[kamacite.docs.collectors.steel.fixtures]

- GIVEN Steel source fixtures contain modules, exports, definitions, contracts, host-function descriptors, examples, and source spans
- WHEN the Steel collector fixture runs or stored evidence is validated
- THEN Kamacite MUST accept matching positive facts and reject stale hashes, undeclared host functions, undeclared capabilities, missing evaluator identities, and overclaims.

### Requirement: Documentation commands support generated documentation lifecycle

r[kamacite.docs.command.collect] Kamacite MUST provide `kamacite docs collect` to collect or validate stored language documentation facts from checked docs configuration without rendering output or executing runnable cells by default.

r[kamacite.docs.command.check] Kamacite MUST provide `kamacite docs check` to validate facts, assemble documentation IR, resolve links, compare receipts, and report deterministic diagnostics without mutating generated artifacts by default.

r[kamacite.docs.command.render] Kamacite MUST provide `kamacite docs render` to render documentation IR projections for admitted target formats while preserving the existing rule that rendered files are projections and not canonical authority.

r[kamacite.docs.command.run_cells] Kamacite MUST provide `kamacite docs run-cells` as the only documentation command mode that may execute runnable examples, and it MUST admit only declared capabilities, evaluator identities, run profiles, and expected outcomes before trusting a cell receipt.

r[kamacite.docs.command.run_cells.wasm] Kamacite MUST provide an explicit WASM execution target for `kamacite docs run-cells`. The WASM target MUST execute only cells with declared WASM runner profiles, module or component identities, engine identities, imports, capabilities, resource limits, and expected outcomes.

r[kamacite.docs.command.update] Kamacite MUST provide `kamacite docs update` as the only documentation command mode that may write generated documentation artifacts, facts, projections, or golden receipts, and it MUST emit an update receipt listing changed identities, diagnostics, checked laws, and non-claims.

#### Scenario: Default docs commands do not execute or mutate

r[kamacite.docs.command.generated_defaults]

- GIVEN an operator runs documentation collection, checking, or rendering without an explicit run-cells or update mode
- WHEN the corpus contains runnable cells or stale generated outputs
- THEN the command MUST report deterministic diagnostics or render to the requested output plan without executing cells or rewriting source docs, generated facts, output directories, fixture manifests, or golden receipts.

### Requirement: Generated documentation fixture admission

r[kamacite.docs.fixture_admission.language_facts_positive] Kamacite MUST include positive fixtures for Rust, Nickel, Steel, cross-language links, generated documentation IR, renderer projections, runnable-cell summaries, documentation receipts, and Valence-friendly exports before claiming autogenerated documentation support.

r[kamacite.docs.fixture_admission.generated_ir_positive] Kamacite MUST include positive fixtures proving that language documentation facts assemble into stable documentation IR with deterministic anchors, links, dependency identities, diagnostics, checked laws, and non-claims.

r[kamacite.docs.fixture_admission.wasm_positive] Kamacite MUST include positive fixtures for WASM-backed Rust, Nickel-adapter, Steel-adapter, and Preserves/Kamacite runnable examples before claiming WASM executable documentation support.

r[kamacite.docs.fixture_admission.language_facts_negative] Kamacite MUST include negative fixtures for unsupported source languages, stale source hashes, missing source envelopes, duplicate item identifiers, duplicate anchors, unknown links, collector identity drift, missing evaluator identities, undeclared capabilities, rendered-output overclaims, and missing non-claims.

r[kamacite.docs.fixture_admission.wasm_negative] Kamacite MUST include negative fixtures for WASM runner drift, undeclared imports, undeclared capabilities, stale module identities, missing engine identities, resource-limit violations, output mismatches, unexpected success, malformed execution receipts, and WASM overclaims.

#### Scenario: Generated docs claims wait for fixture coverage

r[kamacite.docs.autogenerated_validation]

- GIVEN collector code, schemas, or command shells exist without complete positive and negative fixture coverage
- WHEN project documentation describes autogenerated documentation status
- THEN it MUST classify the feature as planned or experimental and MUST NOT claim supported autogenerated documentation.

### Requirement: Autogenerated documentation guidance preserves boundaries

r[kamacite.docs.autogenerated_guidance] Kamacite documentation MUST describe autogenerated documentation as a bounded source-envelope-to-docs-IR pipeline with explicit receipts and non-claims. Guidance MUST state that generated documentation does not prove source-language semantics, evaluator soundness, compiler correctness, runtime behavior, authorization, or rendered-output authority.

#### Scenario: Published guidance names the bounded claim

r[kamacite.docs.autogenerated_guidance.claim_boundary]

- GIVEN README, docs, release notes, or stack evidence mention autogenerated Rust, Nickel, or Steel documentation
- WHEN they describe the supported claim
- THEN they MUST name the bounded documentation facts, documentation IR, projection, and receipt identities rather than claiming whole-program correctness or semantic equivalence.
