## Context

The canonical function-address receipt intentionally excludes display names and paths, but it also excludes `tool_version`, which is normative producer provenance rather than display metadata. Producer and canonicalizer are currently plain strings without descriptor identities.

## Decisions

### 1. Producer profile is content-addressed

**Choice:** Define a producer descriptor containing producer kind, tool version/build identity, canonicalizer profile/version, normative options, and explicit non-claims. Hash canonical descriptor bytes in the adapter/producer domain.

**Rationale:** Receipt consumers need to distinguish evidence generated by materially different producer logic.

### 2. Receipt identity binds producer descriptor identity

**Choice:** Include the descriptor identity in canonical receipt bytes. JSON may display descriptor fields, but projection validation recomputes or resolves the descriptor and rejects disagreement.

**Rationale:** Displayed provenance must not float outside the identity.

### 3. Metadata remains deliberately excluded

**Choice:** Continue excluding path aliases, labels, and display names when their underlying source/function identities are unchanged.

**Rationale:** Names-as-metadata stability remains a stated contract.

### 4. Version the receipt migration

**Choice:** Emit a new receipt/profile version and classify legacy v1 identities as recorded producer evidence with an explicit `tool-version-unbound` caveat.

**Rationale:** Reinterpreting existing hashes as version-bound would be false.

## Risks / Trade-offs

- Producer upgrades intentionally churn receipt identities and downstream references.
- Octet handoff formats need a stable producer descriptor or build identity.
- Build metadata must be normalized so irrelevant packaging paths do not create nondeterminism.
