# Kamacite validation harness

Kamacite now has a walking-skeleton validation harness for the first trusted source-envelope and receipt slice.

Run it through Kamacite's repo-owned package:

```bash
nix run .#kamacite -- validate --root . --manifest fixtures/manifest.json
```

The default mode is non-mutating and receipt-only. Before parsing fixture payloads, reading fixture files, or trusting golden receipts, the CLI validates `fixtures/manifest-generation-receipt.json` against the exact bytes of `fixtures/manifest.ncl`, the closed `fixtures/manifest-contract.ncl`, the supported Nickel evaluator profile/descriptor, and the complete `fixtures/manifest.json` projection. Any source comment/string change, contract drift, metadata change, reordered/duplicate/extra fixture, projection change, evaluator drift, or stale receipt fails closed. Default validation never launches Nickel.

The focused live check evaluates the exact admitted source and contract bytes through an inherited Linux descriptor, validates the closed payload alternatives, and compares the complete generated bytes to the checked projection:

```bash
nix run .#kamacite -- check-manifest-projection --source fixtures/manifest.ncl --contract fixtures/manifest-contract.ncl --projection fixtures/manifest.json
```

Manifest generation and mutation are explicit:

```bash
nix run .#kamacite -- generate-manifest --root .
nix run .#kamacite -- generate-manifest --root . --update
```

Without `--update`, `generate-manifest` runs Nickel and checks the generated projection and receipt without writing. With `--update`, it atomically replaces the projection first and then writes a checked receipt binding source, contract, evaluator, projection, checked laws, and non-claims. A partial write cannot produce trusted success: subsequent receipt-only validation rejects any unmatched projection or receipt.

The explicit Nickel adapter execution mode is:

```bash
nix run .#kamacite -- validate-nickel-adapter --root . --manifest fixtures/manifest.json
```

Only fixtures that declare `execution_mode = "reference-export"` run the Nickel reference CLI. On Linux, the shell runs both `nickel --version` and `nickel export` inside a receipt-bound Bubblewrap profile with a cleared allowlisted environment, isolated network and process namespaces, a read-only Nix runtime closure, descriptor-backed reviewed source/import files, and named `prlimit` CPU, memory, output, diagnostic, and wall-clock budgets. The resulting evidence separately binds requested capabilities, admitted capabilities, shell-observed containment facts, the observed evaluator identity, import identities, bounded output/diagnostic identities, and the process outcome. Limit-triggered process diagnostics are normalized to the receipt-bound outcome class because allocator and signal text can vary across otherwise equivalent bounded runs; ordinary evaluator failures retain their bounded raw diagnostic identity. Import escapes, undeclared inputs/packages, environment dependence, resource exhaustion, and oversized output fail closed; unsupported platforms or unavailable enforcement tools cannot produce trusted live evidence. Default `validate` remains stored-evidence-only and does not silently treat prerecorded export bytes as a fresh Nickel run.

The separate `adapt nickel-export` command never runs Nickel. It admits a pinned `nickel-export-core` v3 manifest, verifies one exact JSON artifact, and checks or explicitly writes canonical packed Preserves bytes plus a receipt through root-confined I/O. See `docs/nickel-preserves-adapter.md`; this value-adaptation receipt does not upgrade producer evidence into arbitrary Nickel source losslessness or semantic equivalence.

The explicit Steel adapter validation mode is:

```bash
nix run .#kamacite -- validate-steel-adapter --root . --manifest fixtures/manifest.json
```

Default `validate` remains receipt-only for Steel fixtures and marks prerecorded output as stored, non-fresh evidence. The explicit command executes each `execution_mode = "dto-probe"` fixture in a fresh Steel 0.8.2 raw no-kernel engine containing only an empty declared `steel/base` module, the admitted `kamacite.add-one` host function, and the exact reviewed source/module/input cohort. It reads the exact source, module descriptor, and fixed profile input through the reviewed root, derives evaluator identity from the embedded runner, applies a named timeout and byte limits, validates input and output against closed content-addressed DTO contracts, and records separate executed-probe goldens. Caller-provided runner labels, undeclared functions/modules, wrong-shaped JSON, failed runs, stale identities, and non-DTO outputs fail closed. The command remains non-mutating unless `--update-golden` is provided. This bounded runner does not prove Steel evaluator soundness, arbitrary Scheme module semantics, bytecode portability, opaque closure serialization, semantic equivalence, or canonical IR authority for JSON/Steel outputs.

The explicit Valence receipt export command is:

```bash
nix run .#kamacite -- export-valence-receipt --root . --receipt fixtures/golden/source-envelope.valid.nickel-minimal.receipt.json --conformance fixtures/valence-export/conformance.json --golden fixtures/valence-export/golden/source-envelope.valid.nickel-minimal.valence-export.json
```

The command reads explicit source receipt, conformance, optional source-span, and optional golden-projection inputs. It calls pure core export logic, reports deterministic JSON, and remains non-mutating by default. `--update-golden` is the only mode that writes a Valence export projection and emits `target/kamacite-valence-export-update-receipt.json` with old/new export identities, source receipt identity, checked laws, and non-claims.

The explicit golden receipt update workflow is:

```bash
nix run .#kamacite -- validate --root . --manifest fixtures/manifest.json --update-golden --update-report target/kamacite-golden-update-receipt.json
```

That mode writes checked golden receipt projections and emits `target/kamacite-golden-update-receipt.json` with old/new receipt identities, input/output identities, covered requirement IDs, and non-claims. It is the only harness mode that rewrites golden fixture evidence. Manifest projection changes remain reviewed source changes and are rewritten only by explicit `generate-manifest --update`.

The Preserves migration workflow is dry-run-first:

```bash
nix run .#kamacite -- migrate-preserves --root . --manifest fixtures/manifest.json --manifest-source fixtures/manifest.ncl
nix run .#kamacite -- migrate-preserves --root . --manifest fixtures/manifest.json --manifest-source fixtures/manifest.ncl --update --report target/kamacite-preserves-migration-report.json
```

The pure core plans canonical packed bytes and typed identity bindings. The update shell performs at most four named convergence passes so receipts that depend on migrated canonical identities are regenerated before the report is accepted. It updates only canonical fixture projections and their explicit manifest identity fields, preserves intentionally stale negative identities, and records whether convergence occurred. If a migration changes either manifest file, run explicit `generate-manifest --update` afterward to evaluate the closed Nickel source and replace the generation receipt. Legacy labeled-JSON identities are retained as compatibility evidence rather than rewritten as Preserves identities.

## Root-relative filesystem confinement

Every command accepting `--root` opens that root once as a directory capability. All manifest, fixture, source, evaluator-input, golden, receipt, Valence, migration, and update-report operations then use the same gateway. Its pure policy rejects empty, absolute, current-directory, platform-prefix, and parent-traversal paths. On supported Linux systems, the shell uses `openat2` with `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS`, and `RESOLVE_NO_MAGICLINKS`; unsupported kernels or platforms fail closed instead of weakening confinement.

Mutation creates a collision-resistant temporary file through the admitted destination-directory handle, flushes it, rechecks that the destination is not a symlink, renames it through that same handle, and flushes the directory. If an attacker replaces the parent pathname after admission, the operation either fails or stays on the already admitted directory object. Explicit fixture-level Nickel execution copies the exact source/import bytes read through admitted handles into inherited anonymous descriptors, so later pathname replacement cannot detach executed bytes from receipt identities. Explicit manifest generation likewise copies the exact admitted source and contract bytes into one inherited anonymous descriptor, so the evaluator cannot reopen ambient joined paths.

`crates/kamacite-cli/src/root_io.rs` owns the audited gateway. Its unit tests cover normal reads, creates, replacements, absolute and parent rejection, source/destination/parent symlinks, destination replacement, and parent replacement. `crates/kamacite-cli/tests/root_io_cli.rs` exercises the validation, adapter, migration, function-address, and Valence command families and verifies outward files remain unchanged.

## Boundary

- `crates/kamacite-core` is the pure deterministic core. It receives in-memory DTOs and bytes, returns deterministic diagnostics and receipts, and does not read files, inspect environment, spawn processes, print, access clocks, access randomness, or mutate state.
- `crates/kamacite-cli` is the thin imperative shell. It reads the manifest projection and fixture bytes, composes with pinned Nickel-export admission for non-executing value adaptation, invokes explicitly declared Nickel fixtures only through the Linux Bubblewrap/prlimit boundary, runs explicit Steel DTO probes in fresh raw engines with only admitted modules and host functions, compares or writes distinct stored/executed golden receipts, and renders JSON reports.
- `fixtures/manifest.ncl` is the reviewed Nickel manifest source for the fixture corpus. `fixtures/manifest-contract.ncl` closes every supported payload alternative and rejects unknown fields. `fixtures/manifest.json` is the exact runtime compatibility projection, and `fixtures/manifest-generation-receipt.json` binds source, contract, supported evaluator, projection, checked laws, and non-claims before the shell consumes it.
- `fixtures/core/**` contains pure in-memory fixtures, including `fixtures/core/fsm/**` for FSM spec, exhaustiveness-receipt, and trace-receipt canonical bytes, plus `fixtures/core/docs/**` for documentation IR, renderer-output, runnable-cell, and documentation-receipt evidence. `fixtures/adapters/nickel/**` contains Nickel export projection bytes for the executable Nickel adapter suite. `fixtures/adapters/steel/**` contains Steel source envelopes, the fixed profile input, module descriptors, DTO outputs, and negative projection fixtures for the bounded Steel adapter suite. `fixtures/valence-export/**` contains reviewed Valence export conformance data, source-span fixtures, negative receipt inputs, and golden export projections. Other adapter/probe execution suites remain deferred until their own changes add declared capabilities and receipt-only modes.
- Documentation validation remains non-executing by default: `documentation-cell` fixtures carry stored outputs or diagnostics, explicit evaluator identities, declared capabilities, and non-claims rather than hidden script execution. See `docs/runnable-docs-pipeline.md`.
